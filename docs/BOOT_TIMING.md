# 启动耗时实测与口径约定（2026-11-06）

机器：Ryzen 7 4800H / 32GB / 无 NVIDIA，`.venv` 已装好，模型在 `models/`。
本文只记**启动**，不涉及说话延迟（那部分见 `END_TO_END_TTFA_AB.md`）。

## 一、三个口径，别混用

| 口径 | 起点 | 2026-11-06 实测 | 用途 |
|---|---|---|---|
| `[boot] 进程总` | 进程拉起（连 `python.exe` 一起算） | **27.6s** | **用户真实等待时间** |
| `[boot] 依赖导入` | 进程拉起 → `app.pipeline` 导入完 | 1.1 – 8.3s | 环境噪声，**不可当验收指标** |
| `[boot] 模型初始化` = `模型就绪，用时` | pipeline `t0`（import 之后） | 20.9s（含 TTS）/ 5–13s（`--no-tts`） | 改动效果只认这个 |
| `[load] xxx 就绪` | 单个模型构造前 | 0.7 – 6.4s | 定位是哪一段慢 |

**踩过的坑**：上一轮拿「进程总」当闸门（要求三次波动 ≤3s），实测 17.7 / 23.6 / 16.4，
极差 7.2s，看起来像改动不稳，其实同一批数据里「模型初始化」只抖 0.2s。
**噪声全在 import 之前**（磁盘/杀毒/页缓存），跟代码无关。

另一个坑：`模型就绪` 在 `--no-tts` 和默认（TTS 开）下**差 15 秒**，
两组数字不能直接相减。凡是要对外说“启动多少秒”，必须注明是否含 TTS。

## 二、本次实测明细（`--mode vad`，TTS 开，等价于双击 `start.bat`）

带时间戳跑 `TranslatePipeline(enable_tts=True)`，单位秒，从进程启动算：

| 时刻 | 事件 | 阶段耗时 |
|---|---|---|
| 0.00 | 进程启动 | — |
| 6.72 | `加载模型中（CPU）…` 出现 | **6.72 依赖导入（全静默）** |
| 8.90 | `[load] paraformer 在线识别就绪` | 2.1 |
| 10.87 | `[load] sensevoice 2pass 就绪` | 2.0 |
| 11.23 | `[load] 加载 MT 模型（2×78MB，首次约 5s）…` | 0.4 |
| 11.77 | `[load] MT 中↔英 就绪` | **0.7**（原来这里是 10.6s 静默） |
| 11.77 | `TTS 预热（中英）…` | — |
| 27.15 | `TTS 预热完成 zh=7616ms en=7329ms` | **15.4（占 56%）** |
| 27.63 | `[punct] loaded … 392ms` | 0.4 |
| 27.64 | `模型就绪，用时 20.9s` | — |
| 27.64 | 之后才是 `双轨实机 VAD：…`（可开口） | **进程总 27.6s** |

对照改动前：37.5s。**净省约 10 秒**，来源是 `app/translate.py` 不再 `import transformers`
（那一步单独实测 10.4–13.4s），改用 `sentencepiece` 直接读 `source.spm` / `target.spm`。

## 三、当前耗时结构：TTS 预热是第一大块

| 阶段 | 耗时 | 占比 |
|---|---|---|
| TTS 预热（中+英两个音色各加载 + 各合成一次 + 50ms 提示音） | 15.4s | **56%** |
| 依赖导入 | 6.7s | 24% |
| Paraformer + SenseVoice 加载 | 4.1s | 15% |
| MT（CT2 ×2）+ 标点 | 1.1s | 4% |

`start.bat` 走 `--mode vad`，即**中→英**。自 2026-11-11 起按 mode 只预热目标音色：

| mode | 预热 |
|---|---|
| `vad` / `ptt` / `file` / `dualsim` | `en` |
| `loopback` | `zh` |
| `duplex` | `zh`+`en` |

未预热语言仍走 `TtsPlayer._load` 懒加载。A/B：`scripts/ab_tts_warmup_langs.py`（闸门：en-only 中位预热 ≤ both−5.0s）。

## 四、CT2 首次构造为什么会抖 0.7–6.4s

连续在干净进程里构造 `ctranslate2.Translator`：

```
run 1: zh_en 6.39s | en_zh 0.18s
run 5: zh_en 6.42s | en_zh 0.18s
先构造 base_ct2 → 6.57s
后构造 lora_ct2 → 0.19s
```

谁先构造谁付这笔钱，两个目录的 `model.bin` 字节数完全相同（79,567,635）。
所以这是 **ctranslate2 的一次性全局初始化**，不是模型体积问题，也不可能消除。
现在用 `[load] 加载 MT 模型（2×78MB，首次约 5s）…` 一行把它交代出来，而不是让用户对着空屏等。

## 五、已知边界：换 tokenizer 后的归一化差异

`app/mt_spm.py` 用裸 `sentencepiece`，绕过了 `MarianTokenizer.normalize()`。166 条中英语料 A/B **DIFF=0**，
但词表外字符行为不同：

| 输入 | `AutoTokenizer`（旧） | `SpmTokenizer`（新） |
|---|---|---|
| `emoji 😀 测试` | `😀` → `<unk>` | `😀` → `😀` |
| `符号 ©®°±×÷` | `©®` → `<unk>` | 原样保留 |
| `日文 こんにちは` | `こんにちは` → `<unk>` | 原样保留 |

- **语音路径零影响**：ASR 只会吐中英文和标点，不会吐 emoji。
- **以后做文本翻译要注意**：粘贴含 emoji 的网页/聊天，两条路径结果可能不同。
  `<unk>` 通常更安全（模型训练时见过 `<unk>`，没见过 `😀` 这个 piece）。
